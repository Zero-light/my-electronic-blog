## 一、变量初值依赖与内存区域

### Q01 — 上电后全局变量未手动初始化的默认值

**场景**：上电后全局变量未手动初始化，默认值是什么？从启动到进入 main，默认值如何确定？

**标准答案**：
默认值是 0（数字 0、字符 `'\0'`、指针 `NULL`）。由启动文件在进入 main 之前，自动将 .bss 段全部清零。

**详解流程**：

```
全局变量 / 静态变量
    │
    ├── 有初值 → 存放在 .data 段（Flash 中存初始值，RAM 中运行）
    │             启动文件从 Flash 拷贝初始值到 RAM
    │
    └── 无初值 → 存放在 .bss 段（RAM）
                  启动文件在进入 main 前将 .bss 段清零
```

**启动文件执行流程**（startup 汇编代码）：
1. 初始化堆栈指针
2. 清零 .bss 段（无初值的全局/静态变量 → 0）
3. 拷贝 .data 段（有初值的全局/静态变量 → 初始值从 Flash 拷入 RAM）
4. 跳转到 `main()`

### 内存布局

| 区域 | 内容 | 生命周期 |
|---|---|---|
| **Flash** | 代码、常量字符串、const 全局变量 | 掉电不丢失，只读 |
| **RAM .data** | 有初值的全局/静态变量 | 全程有效 |
| **RAM .bss** | 无初值的全局/静态变量（启动清零为0） | 全程有效 |
| **RAM 堆** | malloc 动态分配 | 手动管理 |
| **RAM 栈** | 局部变量、函数参数、返回地址 | 函数内有效 |

### Q02 — 局部变量未赋值直接读取

**场景**：局部变量声明后未赋值直接读取，会发生什么？

**标准答案**：
局部变量存放在栈区，未赋值时是随机垃圾值。直接读取会导致逻辑随机错误、判断异常、数值不可预测、程序偶发死机。

> 栈空间不会自动清零，残留的是上次使用的数据。

## 二、static 关键字

### Q03 — static 修饰局部变量

**场景**：static 修饰局部变量后，函数多次调用时变量值如何变化？本质区别？

**标准答案**：
函数多次调用，值会保留上一次结果，不会重新初始化。

**本质**：存储区域从栈 → 静态区（.bss/.data），生命周期变为全程有效。

```c
void counter(void) {
    static int count = 0;  // 存放在 .bss/.data，不在栈上
    count++;
    printf("%d\n", count);  // 第1次调用输出 1，第 2 次输出 2...
}

// 对比普通局部变量（栈上）：每次调用都重新初始化为 0
void counter_no_static(void) {
    int count = 0;  // 栈变量，每次进入函数都重新初始化
    count++;
    printf("%d\n", count);  // 永远输出 1
}
```

### Q04 — 静态全局变量 vs 普通全局变量

**场景**：跨文件访问的区别？

| 类型 | 本文件访问 | 其他文件访问 |
|---|---|---|
| `int g_val;` | 直接访问 | `extern int g_val;` 可访问 |
| `static int g_val;` | 直接访问 | 链接报"未定义引用" |

**本质**：static 限制了作用域为文件内部，外部不可见。

### static 使用总结

| 用法 | 效果 |
|---|---|
| 函数内 static 局部变量 | 值持久化，仅函数内可见 |
| 文件内函数外 static 全局变量 | 仅本文件可见 |
| static 函数 | 仅本文件可调用 |

## 三、const 关键字

### 本质与用法

> **const**：只读修饰符，编译器强制检查，占内存，存在只读段。

```c
const uint8_t A = 8;        // A 不可修改
const uint8_t *P;           // *P 不可修改（地址可变，值不可变）
uint8_t * const P;          // P 不可修改（地址不可变，值可变）
const uint8_t * const P;    // P 和 *P 都不可修改
```

### const vs `#define`

| 维度 | `#define` | `const` |
|---|---|---|
| 处理阶段 | 预处理（字面替换） | 编译 |
| 类型检查 | 无 | 有 |
| 内存占用 | 无（嵌入代码） | 占内存（只读段） |
| 安全性 | 低（无类型保护） | 高（类型安全） |
| 适用场景 | 简单常量宏 | 类型化常量、指针、函数参数 |

### const 使用场景

1. 定义固定不变的参数（从机地址、PI 等）
2. 函数形参保护（防止函数内部修改传入值）
3. 字符串常量固化到 Flash
4. 配置表、固件固定参数表

## 四、volatile 关键字

### 本质

> **volatile**：禁止编译器对该变量做优化。因为有些变量是硬件、外设、中断自己改的，编译器不知道，就会优化掉必要的访问。

### 必须使用 volatile 的场景

```c
// 1. 寄存器地址映射
volatile uint32_t * const UART_DR = (volatile uint32_t *)0x40011004;

// 2. 中断服务函数中使用的全局变量
volatile uint8_t rx_flag = 0;

// 3. 多任务/RTOS 共享的全局变量
volatile uint32_t system_tick = 0;

// 4. 等待硬件状态位、延时等待
while ((UART_SR & TXE) == 0);   // 若不 volatile，编译器可能优化为空循环
```

### 对比不加 volatile 的后果

| 场景 | 无 volatile 后果 |
|---|---|
| 中断标志位 | 编译器认为没人改，优化掉读取 → 死循环等待 |
| 外设寄存器 | 编译器认为值不变，省略重复读 → 状态检测失效 |
| 多任务共享变量 | 编译器优化到寄存器 → 任务间数据不可见 |

## 五、初始化与内存操作

### 初始化顺序

**正确顺序**：时钟 → GPIO → 外设 → 中断

> **第8题**：初始化顺序混乱 → 依赖未初始化 → 配置无效、外设不工作、死机。
> 例：先初始化串口，再开时钟 → 串口配置失效。

### 重复初始化（第9题）

1. 浪费 CPU 执行时间
2. 外设反复重启 → 通信中断
3. 变量反复清零 → 状态丢失
4. 系统实时性下降

### 全局数组初始化后能否自动恢复初始值（第10题）

> 全局数组初始值存储在 Flash（.data 段），运行时占用 RAM。若运行时修改过，不会自动回到初始值。
> 恢复方法：在代码中手动重新赋初值，或将初始值拷贝数组保留在 Flash 中按需还原。

## 六、内存安全

### 字符串拷贝溢出（第25题）

**场景**：拷贝字符串时不限制长度，数据覆盖溢出的过程？

```c
char dest[5];
char src[] = "123456";    // 长度 7（含 '\0'）
strcpy(dest, src);         // 溢出！
```

**执行过程**：
1. 先拷贝目标缓冲区能容纳的部分（dest[0]~dest[4] = '1','2','3','4','5'）
2. 剩余部分继续向目标缓冲区后续的非法内存地址写入（dest[5] = '6', dest[6] = '\0'）
3. **覆盖周边内存** → 目标字符串乱码、周边变量被篡改
4. 若越界覆盖栈数据（如返回地址）→ 程序死机、复位

### 安全替代方案

```c
// 方案1：strncpy（指定最大长度）
strncpy(dest, src, sizeof(dest) - 1);
dest[sizeof(dest) - 1] = '\0';  // 确保以 '\0' 结尾

// 方案2：snprintf（更安全的格式化拷贝）
snprintf(dest, sizeof(dest), "%s", src);

// 方案3：手动边界判断
if (strlen(src) < sizeof(dest)) {
    strcpy(dest, src);
} else {
    // 错误处理
}
```

### 接收协议帧的数据覆盖（第23题）

**场景**：声明了短数组却接收到长数据？

> 短数组无法容纳长数据：
> 1. 先填满数组所有有效下标
> 2. 剩余数据从数组起始位置 **循环覆盖**，或 **越界覆盖周边内存**
> 3. 接收数据完全错乱、原有数据被破坏
> 4. 若越界覆盖关键内存 → 程序死机、复位

### 残留数据干扰（第20题）

**场景**：固定大小接收缓存重复使用，前后两次数据未完全清空？

> 前一次接收的残留数据会与当前接收数据拼接 →
> - 当前接收数据长度误判
> - 数据内容错乱
> - 若残留数据含协议帧头/帧尾 → 协议误解析，出现虚假帧、帧不完整

## 七、数组与指针的本质区别

| 维度 | 数组 | 指针 |
|---|---|---|
| **本质** | 一块连续的内存空间 | 存放地址的变量 |
| **数组名** | 常量地址，不可修改 | 变量地址，可修改 |
| **大小** | `sizeof(arr)` = 元素数 × 类型大小 | `sizeof(p)` = 4/8（与指向内容无关） |
| **函数传参** | 退化为指针 | 直接传递地址 |
| **取地址 `&arr`** | 整个数组的地址（步长 = 数组总大小） | 指针变量的地址（步长固定） |

```c
int arr[5] = {1, 2, 3, 4, 5};
int *p = arr;

sizeof(arr);      // 20（5 × 4 字节，假设 int 为 4 字节）
sizeof(p);        // 4 或 8（平台字长）
&arr + 1;         // 跳过整个数组（+20 字节）
&arr[0] + 1;      // 跳到下一个元素（+4 字节）
&p;               // 指针变量 p 本身的地址
```

## 八、UART 接收流程与错误处理

### 接收数据完整流程

```
串口RX引脚有数据
    │
    ▼
硬件中断触发（USART_IRQn）
    │
    ▼
HAL_UART_IRQHandler()
    │
    ├── 接收完成 → HAL_UART_RxCpltCallback()
    │
    └── 错误发生 → HAL_UART_ErrorCallback()
```

### 串口错误导致中断死循环的问题

**常见问题**：语音模块静置空闲时，串口中断不停进入，一直自动乱发数据。

**根因**：
- STM32 串口只要 RX 引脚浮空、电磁干扰、电平抖动 → 产生 ORE（溢出错误）、FE（帧错误）
- 一旦 ORE/FE 置位 → **硬件锁死中断**，永远不停进中断

**ORE/FE 特性**：
- 锁存型：一旦置位，会保持，直到主动清除
- 当 ORE/FE/PE 标志位为 1 时，串口外设会**持续**向 NVIC 发送中断请求

**解决方案**：
1. 在 `HAL_UART_ErrorCallback` 中清除错误标志
2. 重置接收状态机
3. 重启接收中断

### 回调函数机制

**回调函数定义步骤**：
1. 定义回调函数类型（函数指针类型）→ `void (*A)(void)`
2. 用该类型定义变量 → `A B;`（B 就是函数指针变量）
3. 创建注册函数，将要执行的函数名传给 B → `B = callback_func;`
4. 写回调函数内容 → `void callback_func(void) { ... }`
5. 在中断/其他代码中调用 `B()` → 等效于调用 callback_func

**回调函数类型**：
- 错误回调：处理 ORE、FE、PE 错误
- 接收回调：仅处理正常接收

## 九、通信业务中加入超时判断

### 有超时 vs 无超时流程对比

```
无超时流程：
发送数据 → 等待接收 → 永远卡死在"等待接收"（若对端无响应）

有超时流程：
发送数据 → 启动定时器 → 等待接收
    │                  │
    ├── 超时到达 → 超时处理/重发/报错
    │
    └── 接收成功 → 停止定时器 → 处理数据
```

## 十、校验与错误处理

### 异或校验（第33题）

> 分步位运算的标准执行流程：校验字节与数据段每个字节依次异或，最终结果为校验值。

```c
uint8_t calc_xor_checksum(uint8_t *data, uint8_t len) {
    uint8_t checksum = 0;
    for (uint8_t i = 0; i < len; i++) {
        checksum ^= data[i];   // 依次异或
    }
    return checksum;
}
```

### 异常数据导致解析死锁（第34题）

> 串口接收未做容错处理，异常数据使程序卡死在解析循环中：
> - 缺少帧头/帧尾 → 解析状态机永远等不到完整帧
> - 数据长度字段异常 → 超出缓冲区仍继续拷贝
> - 缺少超时退出 → while 循环永不退出
>
> 解决：加入超时退出机制 + 帧完整性校验 + 边界检查

| 知识点 | 核心要点 |

| 全局变量默认值 | 0，由启动文件清零 .bss 段 |
