## 一、HardFault 与异常分析

### Q01 — HardFault 的完整分析方法

**📐 L1　💡 高频：是　🔗 关联：01-Q17（UB）、02-Q10（启动流程）**

**场景**：你的程序随机 HardFault，如何定位是哪一行代码导致的？

**答案**：
```
1. 在 HardFault_Handler 中抓取关键寄存器：
   - MSP/PSP：确定是哪个栈
   - LR（EXC_RETURN）：确定返回模式
   - PC（通过栈帧定位）：确定Fault地址
   - SCB->CFSR（Configurable Status Register）：确定Fault类别

2. 常见 Fault 类型：
   - IACCVIOL：指令访问违规（跳到非法地址）
   - DACCVIOL：数据访问违规（读/写非法地址）
   - INVPC：无效 PC 加载（函数指针跳转错误）
   - UNALIGN：非对齐访问（仅 M0 有效）
   - STKOF：栈溢出

3. 定位代码行：
   - 使用 addr2line 工具：arm-none-eabi-addr2line -e firmware.elf <PC>
   - 或使用 GDB 的 list *<PC> 命令
```

### Q02 — HardFault_Handler 中如何自动抓取栈帧

**📐 L2　💡 高频：是　🔗 关联：08-Q01**

**答案**：
```c
__attribute__((naked)) void HardFault_Handler(void)
{
    __asm volatile(
        "tst lr, #4        \n"  // 检查 EXC_RETURN 的 bit2
        "ite eq             \n"
        "mrseq r0, msp      \n"  // bit2=0，使用 MSP
        "mrsne r0, psp      \n"  // bit2=1，使用 PSP
        "b hard_fault_handler_c \n"
    );
}

void hard_fault_handler_c(uint32_t *stack_frame)
{
    uint32_t r0  = stack_frame[0];
    uint32_t r1  = stack_frame[1];
    uint32_t r2  = stack_frame[2];
    uint32_t r3  = stack_frame[3];
    uint32_t r12 = stack_frame[4];
    uint32_t lr  = stack_frame[5];   // Link Register
    uint32_t pc  = stack_frame[6];   // Program Counter ← 导致 Fault 的地址
    uint32_t psr = stack_frame[7];
    
    // 读取 Fault 状态寄存器
    uint32_t cfsr = SCB->CFSR;
    uint32_t hfsr = SCB->HFSR;
    uint32_t mmfar = SCB->MMFAR;
    uint32_t bfar = SCB->BFAR;
    
    // 记录故障信息（可写入 Flash 或 UART 输出）
    fault_log(FAULT_HARD, pc, cfsr, hfsr);
    
    // 系统复位或进入安全状态
    HAL_NVIC_SystemReset();
    while(1);
}
```

### Q03 — 栈溢出导致 HardFault 的排查

**📐 L2　💡 高频：是　🔗 关联：01-Q10、02-Q14、05-Q15**

**场景**：你的任务有时运行正常，有时 HardFault，怀疑栈溢出。

**答案**：
```
排查步骤：
1. 启用 FreeRTOS 的栈溢出检测（configCHECK_FOR_STACK_OVERFLOW=2）
2. 在 vApplicationStackOverflowHook 中设置断点
3. 检查 uxTaskGetStackHighWaterMark() 的返回值
4. 如果接近 0，增大任务栈大小

常见原因：
- 函数中定义大数组（如 uint8_t buf[1024]）
- 递归调用
- 嵌套调用太深
- 局部大结构体（在函数内定义的结构体变量在栈上分配）

// ❌ 危险：大局部数组
void process_frame(void)
{
    uint8_t temp[4096];  // 4KB 栈空间！如果任务栈只有 2KB...
    // ...
}

// ✅ 正确：使用 static 或全局
static uint8_t temp[4096];
void process_frame(void)
{
    // 使用 temp
}
```

## 二、运行时故障

### Q05 — 系统时钟配置错误导致的"玄学"问题

**📐 L2　💡 高频：否　🔗 关联：02-Q07、02-Q08**

**场景**：你的程序在调试时正常，全速运行后发现 UART 波特率偏高或偏低。

**答案**：
```
原因分析：
- UART 波特率 = f_CK / (8 × (2 - OVER8) × USARTDIV)
- 系统时钟越高，波特率计算中的分频系数需要调整
- 如果 SystemClock_Config() 配置错误，外设时钟可能不对
- 调试器可能强制 HSI 作为时钟源，掩盖了问题

排查：
1. 在 main() 中尽早读取 SystemCoreClock 变量
2. 检查 RCC 寄存器（CFGR, CR, PLLCFGR）
3. 使用 MCO 引脚输出时钟，用示波器测量
```

### Q06 — 非对齐访问导致的 M0 HardFault

**📐 L2　💡 高频：否　🔗 关联：01-Q11、04-Q14**

**场景**：你将 STM32F1 的代码移植到 STM32L0（M0+），发现 HardFault。

**答案**：
```
原因：M0/M0+ 不支持非对齐访问
代码中可能有：
- uint16_t val = *(uint16_t*)(buf+1);  // 奇数地址
- uint32_t val = *(uint32_t*)(buf+1);  // 非 4 字节对齐

解决：
1. 使用 memcpy 替代直接指针访问
2. 确保 DMA 缓冲区和外设数据宽度匹配
3. 使用 __packed 时要格外小心
4. 可以使用 SCB->CFSR 的 UNALIGN_TRP 位来检测
```

### Q07 — FreeRTOS 中断优先级配置错误导致系统崩溃

**📐 L2　💡 高频：是　🔗 关联：03-Q02、05-Q11**

**场景**：你的 FreeRTOS 系统在高频中断下随机崩溃。

**答案**：
```
原因分析：
FreeRTOS 只管理优先级在 configLIBRARY_MAX_SYSCALL_INTERRUPT_PRIORITY 
及以上的中断。如果将某个中断配置为可管理优先级范围内，
该中断可以调用 FromISR 函数。如果该中断优先级太低
（数值 < configLIBRARY_MAX_SYSCALL_INTERRUPT_PRIORITY），
它不受 FreeRTOS 管理，调用 FromISR 函数会导致：
- xTaskGetTickCountFromISR() 返回错误值
- 临界区嵌套计数错误
- 上下文切换在错误时机触发

解决：
1. 所有调用 FreeRTOS API 的中断优先级必须设置正确
2. 使用configASSERT() 捕获优先级错误
3. 优先级分组使用 Group 4（全抢占优先级）
```

### Q08 — ADC 采样值跳变的排查

**📐 L2　💡 高频：否　🔗 关联：04-Q08、04-Q10**

**场景**：你的 ADC 采样值偶尔跳变很大。

**答案**：
```
排查步骤：
1. 检查参考电压是否稳定（VREF+ 引脚上的电容）
2. 检查采样时间是否足够（高阻抗源需要更长采样时间）
3. 检查 PCB 布局（模拟信号远离开关信号）
4. 检查电源纹波（LDO 输出是否有足够去耦）
5. 检查 ADC 时钟是否超过最大允许值（36MHz for 12-bit）
6. 检查 DMA 缓冲区是否有 Cache 一致性问题（M7）

软件改善：
1. 使用平均滤波（滑动平均或中值滤波）
2. 开启 ADC 硬件过采样
3. 在 ADC 输入前添加 RC 低通滤波
```

```c
void log_itm(const char *msg)
```

### Q10 — 使用 DWT 周期计数器进行精确测量

**📐 L2　💡 高频：否　🔗 关联：02-Q02**

**场景**：你需要测量一段代码的执行时间。

**答案**：
```c
// 启用 DWT 周期计数器
void dwt_init(void)
{
    CoreDebug->DEMCR |= CoreDebug_DEMCR_TRCENA_Msk;
    DWT->CYCCNT = 0;
    DWT->CTRL |= DWT_CTRL_CYCCNTENA_Msk;
}

// 测量代码执行时间
void measure_function(void)
{
    uint32_t start = DWT->CYCCNT;
    
    // 被测代码
    HAL_UART_Transmit(&huart1, data, len, 1000);
    
    uint32_t cycles = DWT->CYCCNT - start;
    float us = (float)cycles / (SystemCoreClock / 1000000.0f);
    printf("Execution time: %.2f us\n", us);
}
```

```python
class HardFaultAnalyzer(gdb.Command):
    def __init__(self):
        super().__init__("analyze-fault", gdb.COMMAND_USER)
    
    def invoke(self, arg, from_tty):

        lr = gdb.parse_and_eval("$lr")

        # 定位代码行
        gdb.execute("list *{}".format(pc))

HardFaultAnalyzer()
end
```

## 四、优先级翻转故障

### Q12 — 优先级翻转导致系统卡死

**📐 L2　💡 高频：是　🔗 关联：05-Q12、05-Q06**

**场景**：你的三个任务按优先级分工，但高优先级任务偶尔超时。

**答案**：
```
故障现象：
- 高优先级任务 H（电机控制，优先级 4）
- 中优先级任务 M（数据处理，优先级 3）
- 低优先级任务 L（传感器采集，优先级 2）

L 获取 SPI 互斥量 → M 抢占 L → H 请求 SPI 互斥量被阻塞
→ M 长时间运行 → H 超时未执行 → 电机故障

根因：
1. 使用二值信号量保护 SPI → 没有优先级继承
2. L 的优先级低于 M，M 可以无限抢占 L
3. H 被间接阻塞

解决：
1. 将二值信号量替换为互斥量（带优先级继承）
2. 或提升 L 的优先级到不低于 H
3. 或拆分 SPI 访问，减少 L 持有互斥量的时间
4. 使用二值信号量 + 临时优先级提升（手动实现优先级继承）
```

### Q13 — 优先级翻转在 RTOS 中的间接危害

**📐 L3　💡 高频：否　🔗 关联：08-Q12、05-Q12**

**场景**：你发现即使使用了互斥量，高优先级任务仍然偶尔超时。

**答案**：
```
"连锁阻塞"（Chained Blocking）：
如果 L 持有互斥量 A，同时需要获取互斥量 B，
而 B 被另一个任务持有，则问题更复杂。

解决：
1. 资源排序：所有任务以相同顺序获取多个互斥量
2. 使用互斥量的同时限定最大持有时间
3. 在获取互斥量前提升自身优先级
4. 设计时尽量减少互斥量的持有时间
```

## 五、时序相关故障

### Q14 — 关键段与中断延迟导致的 PWM 抖动

**📐 L2　💡 高频：否　🔗 关联：03-Q04、04-Q05**

**场景**：你的电机控制 PWM 周期偶尔跳动。

**答案**：
```
原因：在更新 PWM 寄存器（ARR/CCR）时，被高优先级中断打断
导致更新时机不一致。

解决：
1. 在更新 PWM 寄存器时短暂关中断（不是整个系统）
2. 使用定时器的预装载（Preload）功能，在下一周期生效
3. 使用 DMA 批量更新 PWM 寄存器

// 使用预装载：在更新事件时同步写入
TIM2->CR1 |= TIM_CR1_ARPE;  // ARR 预装载使能
TIM2->CCMR1 |= TIM_CCMR1_OC1PE;  // CCR 预装载使能
// 写入 ARR/CCR 后，在下一周期生效，不被中断打断
```

### Q15 — Cache 一致性问题导致 ADC 数据错误（M7）

**📐 L2　💡 高频：否　🔗 关联：03-Q10、04-Q10**

**场景**：在 STM32H7 上使用 ADC DMA，偶尔读到旧数据。

**答案**：
```
场景：
- ADC 通过 DMA 将数据写入缓冲区（SRAM_D1）
- CPU 有 D-Cache 缓冲
- CPU 读取时命中 Cache（旧值）而非内存

DMA 写入内存 → 新数据在内存中，但在 Cache 中是旧值

解决：
1. 将 ADC 缓冲区放在 Non-Cacheable 区域（通过 MPU 配置）
2. DMA 写入后调用 SCB_InvalidateDCache_by_Addr()
3. DMA 读取前（MEMORY2PERIPHERAL）SCB_CleanDCache_by_Addr()
```

### Q16 — 中断丢失导致的按键误触发

**📐 L2　💡 高频：否　🔗 关联：03-Q06、04-Q01**

**场景**：你的按键在中断中检测，偶尔一次按下被识别为多次。

**答案**：
```
原因：
- 按键抖动导致多次上升沿/下降沿触发
- 或中断优先级太低，被打断后又重新进入

解决：
1. 硬件去抖：RC 滤波电路
2. 软件去抖：在中断中启动定时器，延时 20ms 后检测
3. 使用状态机：在中断中设置标志，在任务中延时检测

// 中使用状态机：在中断中设置标志
void EXTI0_IRQHandler(void)
{
    __HAL_GPIO_EXTI_CLEAR_IT(GPIO_PIN_0);
    
    // 设置标志，不直接处理
    button_event = 1;
    button_tick = HAL_GetTick();
}

// 在任务中检测（去抖）
void button_task(void *param)
{
    while (1) {
        if (button_event && (HAL_GetTick() - button_tick > 20)) {
            button_event = 0;
            if (HAL_GPIO_ReadPin(BUTTON_GPIO_Port, BUTTON_Pin) == GPIO_PIN_SET) {
                // 确认按键按下
                handle_button_press();
            }
        }
        vTaskDelay(pdMS_TO_TICKS(5));
    }
}
```

## 六、综合大型案例

### Q17 — 一套完整的多故障并发案例

**📐 L3　💡 高频：否　🔗 关联：贯穿全文件**

**场景**：你的设备在客户现场出现以下现象：
- 偶尔自动重启
- 偶尔 ADC 采样值异常
- 偶尔 UART 通信中断
- 偶尔按键失灵

**答案**：
```
根因分析：
1. 自动重启 → 看门狗复位或 HardFault
2. ADC 异常 → 电源纹波或采样时间不足
3. UART 中断 → 通信线路干扰或超时处理不当
4. 按键失灵 → 去抖不足或中断优先级配置

实际案例：这些现象可能有一个共同根因 — 电源质量差！
- 电池电压不稳 → ADC 参考电压变化 → ADC 值异常
- 电压跌落到欠压阈值 → 看门狗复位
- 电源噪声耦合到数字线路 → UART 误码
- 电压不稳定导致 GPIO 检测不稳定

解决：
1. 检查电源质量（示波器测纹波）
2. 增强 LDO 前级滤波电容
3. 在 ADC 中断中增加滤波算法
4. 在 UART 通信中增加超时重试
5. 在按键检测中增加去抖
```

### Q18 — 长时间运行后内存泄漏导致死机

**📐 L3　💡 高频：否　🔗 关联：01-Q10、05-Q14**

**场景**：你的设备运行 72 小时后死机。

**答案**：
```
排查：
1. 检查 FreeRTOS 的 uxGetFreeHeapSize() 或 mallinfo()
2. 在每次 pvPortMalloc()/vPortFree() 中记录
3. 检查是否有只分配不释放的场景

常见原因：
- 在任务中动态分配内存但忘记释放
- 使用第三方库（如 JSON 解析）后没有调用清理函数
- 在中断中调用 pvPortMalloc（不允许）

解决：
1. 使用静态分配替代动态分配
2. 如果必须动态分配，记录分配/释放日志
3. 使用内存池（memory pool）替代 malloc
4. 启用 FreeRTOS 的 trace 功能（traceMALLOC/traceFREE）
```

## 七、调试方法论总结

### Q19 — 系统化的调试思路

**📐 L1　💡 高频：否**

**答案**：
```
1. 收集信息
   - 故障现象是什么？
   - 是否可复现？
   - 何时开始出现？
   - 做了什么改动后出现的？

2. 定位范围
   - 硬件问题 vs 软件问题
   - 电源问题 vs 通信问题
   - 时序问题 vs 逻辑问题

3. 缩小范围
   - 二分法注释代码
   - 使用断点/日志定位
   - 使用示波器/逻辑分析仪

4. 根因分析
   - 为什么会出现这个问题？
   - 如何防止再次出现？
   - 是否有类似问题？

5. 修复与验证
```
